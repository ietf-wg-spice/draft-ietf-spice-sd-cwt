Coverage

All six canonical examples, not just the worked one

issuer_cwt.cbor and kbt.cbor are the draft’s worked example and reach neither decoys nor nesting. The other four do, and they are where a plausible-looking implementation comes apart.

Nesting has to be resolved iteratively. Revealing one disclosure exposes Redacted Claim Hashes inside its value, which later disclosures then match. A checker that tests every disclosure against only the outermost hashes reports 3 of 15 on nested_issuer_cwt.cbor and looks like a library bug. It is the checker that is wrong — and it is the same reason the every-disclosure-must-be-used rule has to run after reconstruction, never before.

What interop testing found

Thirty-two defects that every existing test passed

Both suites were green throughout. They sign and verify with the same code on both sides, so they prove self-consistency, not conformance. Nothing compared against bytes the implementation did not produce itself.

sd-cwt

17

python · 90 tests green while broken

  • Disclosure hash over the wrong bytes. The CDDL input is bstr .cbor salted-entry; the digest must cover the byte string including its header.
  • Payload double-encoded on issuance. The verifier carried a workaround for exactly this, which is why it went unnoticed.
  • Could not verify or sign ES384. Verification hardcoded ES256; signing had no ES384 signer at all, so the draft’s own issuer key was unusable in both directions.
  • A sample URL in every credential, as a tstr where the CDDL requires bstr. That one claim failed CDDL validation for every token produced.
  • Duplicate map keys resolved last-one-wins, silently — how two parties are made to read the same bytes differently.
  • An issuer that returned b'dummy_signature_placeholder' in the signature slot, under the same class name as the real one.

sd-cwt-js

15

javascript · 456 tests green while broken

  • Four registered code points wrong. sd_alg written at 18 rather than 170, so a conforming verifier would never find the hash algorithm; also 19→171, 20→172, decoy tag 61→62.
  • ES384 and ES512 silently used SHA-256. Both sides wrong in the same direction, so round-trips passed. The browser shim was correct, so the two builds disagreed with each other.
  • Unused disclosures were dropped with a warning where the spec requires the token be rejected — a holder could attach disclosures from another credential.
  • Empty sd_claims emitted and accepted, where the spec requires it be omitted and treated as invalid.
  • CBOR tags flattened to plain objects in custom headers, losing the tag number entirely.
  • Indefinite-length CBOR and duplicate keys accepted; nested tags, k alongside 58(k), and non-finite times all accepted at issuance.

esdicawt

2 / 6

rust · two fixed upstream, four open

  • Fixed: kcwt is now the embedded #6.18 rather than a bstr (issue 94), and the disclosure digest now covers the bstr. With those two in, it verifies the draft’s own SD-KBT and a javascript-issued presentation.
  • Emits indefinite-length CBOR. The SD-KBT unprotected header is written bf ff where the draft writes a0. Section 6.4 says encoders MUST NOT send it and decoders MUST reject it, so both other implementations refuse the token — independently, and for exactly this reason.
  • The status claim is mandatory when the status feature is on: every other claim on the payload is Option with a default, that one is not. The draft’s CDDL does not list status in sd-payload at all, so no canonical example carries it and none of them parse.
  • A trait bound still excludes P-256 and P-384 Holder keys from the verifier API, including the draft’s own Appendix C key. It exists to serve an Ed25519-only fast path that already holds the key it needs.
  • To Be Decoy is 61, and should be 62 per Section 17.3.
  • Its draft-example tests are still #[ignore]d and its submodule still points at -05, so none of the above surfaces in CI.
The bug three implementations shared, and why

All three computed the Redacted Claim Hash over the bare salted-entry array instead of the CBOR byte string that wraps it. Independently, in three languages.

The reason is in the draft. Section 3 walks a reader through the worked example, and the digest it prints there disagrees with the token printed a page earlier:

section 3 walkthrough  d9df03da474fcb3c65771748e2e0608c…   ← hash of the bare array
the token itself       af375dc3fba1d082448642c00be7b2f7…   ← hash of the bstr

The normative text is unambiguous — the CDDL says bstr-encoded-salted = bstr .cbor salted-entry, and Appendix A step 2 says to hash that structure. Only the generated example file first-blinded-hash.txt disagreed. But a reader following the walkthrough hand-implements the wrong digest, which is what happened here three times over. All three now match the token.

The example itself is being corrected in PR 297, which regenerates the Section 3 walkthrough from the bstr and prints the two-byte header above the array, so the digest a reader computes by hand is the one the token carries.

Method

How to reproduce this

Every cell was produced by running code, not by reading it. The inputs are this repository’s own examples/*.cbor and the Appendix C keys, unmodified.

CheckHow it is decided
Verify an example COSE_Sign1 signature verifies under the Appendix C key, and every disclosure in sd_claims resolves to a Redacted Claim Hash present in the payload.
Present a credential A subset of the Issuer’s disclosures is selected, a new SD-KBT is signed with the Appendix C Holder key, and the result verifies end to end.
Issue A token is produced with the P-384 Issuer key and read back by a different implementation.
CDDL conformance Produced tokens are validated against sd-cwts.cddl with the Ruby cddl tool already vendored for make validate.
Normative probe Thirteen MUST / MUST NOT statements are each exercised with a token that violates them; the implementation must reject it.

This page is informational. It records what independent implementations were observed to do at a point in time. It is not part of the specification, it does not add or interpret requirements, and where it disagrees with the draft, the draft is correct.

The boundary

What this does not yet confirm

AEAD disclosures

unimplemented in all three

  • sd_aead_encrypted_claims (171) and sd_aead (172) are optional and nobody has built them.
  • The draft ships this example as EDN only, with no signed .cbor vector, so there is nothing to interoperate against yet.

esdicawt, outbound

one defect from a complete matrix

  • Inbound is done: it reads the draft’s presentation and a javascript-issued one.
  • Outbound is blocked only by the indefinite-length unprotected header. bf ff becoming a0 closes the last cell.

Coverage edges

not exercised

  • sd_alg values other than SHA-256.
  • Thumbprint-style cnf (confirmation key 3) end to end.
  • sd-cwt-js has no test workflow, so its 471 tests never run on a pull request.
  • Neither python nor javascript is registered in this repository’s own interop/ harness, so the working group cannot yet reproduce their columns.
